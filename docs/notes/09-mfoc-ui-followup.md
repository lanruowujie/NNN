# 规格 09 UI 验收跟进

日期：2026-09-13

## 实际完成内容

- 修复密钥扫描尚未找到匹配项时，后端因 `omitempty` 不发送零值 `found`，前端把缺失字段显示成 `undefined` 的问题；缺失值现在明确显示为 `0`。
- “原始日志”入口改为始终可用。没有外部进程输出时仍可打开，并显示“尚无外部进程输出”；开始新任务会清空上一任务的原始输出，但不会禁用入口。
- MFOC 启动确认改用应用内 dialog，并在提交 binding 前立即显示“正在启动”，避免原生 WebView 确认框或短暂可用性检查表现为点击无响应。
- 根据用户的明确选择，MFOC stdout/stderr 不再隐藏完整密钥；原始日志和活动日志会显示工具实际输出。
- 首次真实运行发现固定的 MFOC 0.10.7 不支持假定的 `-f` 字典参数。适配器已改为使用该版本帮助中声明的可重复 `-k <key>` 参数，并让运行时可用性检查同时确认此选项；fake MFOC 和参数测试同步采用真实 CLI 形态，避免测试替身再次掩盖接口偏差。
- 真实 Nested 恢复成功后发现 MFOC 0.10.7 即使面对 Classic 1K，也会把固定 4096 字节的 `mifare_classic_tag` 写入输出文件。适配器现在只在后 3072 字节全零时接受这一上游兼容格式并安全截取前 1024 字节；fake 改为复现该行为，测试同时覆盖非零尾部拒绝。

## 实现过程中遇到的问题

- `attempted` 大于零时前端进入扫描进度分支，但 `found=0` 会被 Go JSON 的 `omitempty` 省略。前端类型原本允许该字段缺失，显示时却没有提供零值回退。
- 早期 fake MFOC 自行定义了上游不存在的 `-f` 参数，导致自动化测试没有覆盖固定二进制的真实命令行契约。现在可用性检查和 fake 都以打包二进制的 `-h` 输出为准。

## 阻塞或未完成事项

- 无。2026-09-13，用户在 PN532 + FT232RL 和自有随机密钥 Classic 1K 测试卡上复验通过：以一个已知 Key A 值启动后，MFOC 实际进入 Nested、恢复未知 Key B，NFCX 完成复验和读取，规格 09 验收结束。
