# 规格 02：固定 libnfc 工具链

## 目标

选择、固定并可复现地构建 NFCX 使用的 libnfc 版本，为主进程 CGO 和后续外部破解工具提供同一套驱动和运行时依赖。

## 前置条件

- 规格 01 已验收。
- 当前开发平台具备 C 编译工具链。

## 范围

- 固定 libnfc 上游仓库、版本和 commit。
- 保存补丁及其用途说明，不直接修改无法追踪的 vendored 源码。
- 在当前平台构建 libnfc 和必要依赖。
- 优先启用 `pn532_uart`，并根据平台启用 `pn53x_usb`、`acr122_usb`、PC/SC。
- 定义 `runtime/<os>-<arch>` 的文件布局。
- 提供开发环境检测脚本或 Go 工具，报告头文件、库和运行时缺失情况。
- 记录许可证和源码获取方式。

## 不在本阶段实现

- Go CGO binding；
- GUI 设备列表；
- mfoc/mfcuk；
- 自动发布所有平台产物。

## 实现要求

必须记录：

- libnfc upstream URL；
- commit SHA；
- configure/CMake 参数；
- 启用的驱动；
- 依赖的 libusb/PCSC 版本或系统要求；
- 构建产物的许可证；
- 对上游应用的全部补丁。

开发和运行时文件必须分开：头文件和链接文件供构建使用，动态库供应用运行使用。运行时文件不得依赖开发者机器上的绝对路径。

PN532 + FT232RL 的连接字符串通过配置或环境传入，例如 `pn532_uart:<serial-port>`，不得写死现有脚本中的 `/dev/cu.usbserial-A50285BI`。

如果当前平台是 macOS arm64，本阶段必须先在这一平台跑通；其他平台可以暂时只有构建设计，但所有脚本要避免写死 macOS 路径。

## 自动化测试

- 构建脚本能在干净临时目录重复执行；
- 产物检查能确认目标动态库存在；
- 可以编译并运行一个最小 C 程序调用 `nfc_init` 和 `nfc_exit`；
- 没有设备时程序正常报告零设备或明确错误，而不是崩溃。

## 手工硬件验收

使用项目现有 PN532 + FT232RL：

1. 指定实际串口对应的 connstring；
2. 使用 libnfc 的扫描工具确认 PN532；
3. 放置测试卡，确认可以输出 UID/ATQA/SAK；
4. 重复插拔读卡器后再次成功识别。

## 验收标准

- [x] libnfc 来源、commit、构建参数和许可证已记录。
- [x] 当前平台能重复构建 libnfc。
- [x] `pn532_uart` 驱动已确认启用。
- [x] 动态库不存在对开发者私有绝对路径的引用。
- [x] 最小 C smoke test 通过。
- [ ] PN532 + FT232RL 可通过 libnfc 寻卡。
- [x] 未修改用户系统级 libnfc 配置。
