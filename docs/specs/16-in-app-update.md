# 规格 16：低打扰的应用内更新

## 目标

让 NFCX 能在不打断 NFC 工作流的前提下检查、下载并在用户选择的重启时应用稳定版更新。更新入口必须融入现有主窗口、顶部状态和“关于 NFCX”对话框；不得为“发现新版本”弹出模态窗口，也不得把普通 HTML 链接当作更新入口。

用户应该感受到的是：NFCX 安静地知道有更新、在用户允许后准备好更新、并且只在安全空闲时请求重启。

## 前置条件

- 规格 12 的签名、发布、私有 runtime 和 `manifest.json` 流程已可用。
- macOS 正式发行版已采用 Developer ID 签名及公证；Windows 正式发行版已采用受信任的代码签名。未签名构建不可自动应用更新。

## 范围

- 稳定通道的静默检查、版本比较、后台下载、验签、准备重启和平台更新辅助程序。
- 当更新无法安全应用时的明确降级：保留“下载到本机并在文件管理器中显示”，不跳转浏览器。
- 在现有 About 对话框、顶部栏和任务状态区域中显示更新状态。
- 三个平台对可自动更新的发行格式做出明确区分。

## 不在范围内

- 自动安装 prerelease、nightly 或用户自行编译的构建。
- 未经用户明确选择而消耗网络流量下载完整安装包；“自动下载更新”是设置项，默认关闭。
- 更新系统配置、用户密钥库、dump、日志或任何 NFC 数据。
- NFC 任务执行中暂停、杀死或重启应用。
- 通过 GitHub Releases 网页或 API 返回的 tag 直接信任可执行文件。

## UX 规则

### 检查频率

- 首次启动后，窗口已经可操作且没有进行 NFC 任务时，在后台检查一次。
- 后续最多每 24 小时自动检查一次；失败采用指数退避，最长 7 天。手动检查不受该节流限制。
- 网络请求超时、离线或服务端异常都静默失败；不显示 toast、弹窗或错误日志。
- 检查更新不依赖遥测开关，也不携带 installation ID、读卡器、卡片、密钥、dump 或本地路径。

### 发现更新

发现稳定版更新后不得立即弹窗。现有顶部栏在不改变布局的前提下显示一个紧凑、可关闭的更新胶囊：`新版本 1.2.0`。它只提供一个入口，点击后打开现有“关于 NFCX”对话框的更新区。

About 的原“检查更新”区域替换为以下状态，不再渲染外部链接：

| 状态 | About 区域 | 顶部栏 |
| --- | --- | --- |
| 未检查 / 已是最新 | `检查更新` 次按钮；显示当前版本 | 不显示 |
| 正在检查 | 禁用的 `正在检查…` | 不显示 |
| 有更新，尚未下载 | `NFCX 1.2.0 已可用`、发行说明摘要、`后台下载` 主按钮、`稍后` | 显示可关闭胶囊 |
| 正在下载 | 进度、已下载大小、`取消下载` | 仅显示进度图标，不能遮挡任务状态 |
| 已准备好 | `更新已准备好，重启后安装`、`重启并更新` 主按钮、`稍后` | 显示 `更新已就绪` |
| 无法自动应用 | 原因及 `显示已下载文件`；没有浏览器链接 | 显示可关闭胶囊 |

`稍后` 和关闭胶囊只隐藏当前版本的提示；同一个版本在同一次运行中不再主动提示。About 中仍可查看并操作。新版本到达时重置该抑制状态。

### 下载与重启

- 用户点击 `后台下载` 才开始下载，除非其已在设置中打开“自动下载稳定版更新”。
- 下载开始后立即回到原来的 NFC 工作界面；进度只反映在 About 和顶部小图标中。
- 下载不得和读卡、写卡、密钥恢复或外部攻击引擎争抢设备；更新不访问读卡器。
- `重启并更新` 仅在没有活动任务、没有待确认的危险写入和没有未保存工作副本时可用。
- 若工作副本有未保存修改，先复用已有的“保存/放弃/取消”确认流程；用户取消则保持更新已准备好。
- 若有 NFC 任务，按钮文案为 `任务完成后可更新` 并禁用。任务完成后恢复可用，但不自动重启。
- 关闭应用时，若更新已准备好且当前安全退出，显示一次简短选择：`安装更新后退出`、`直接退出`、`取消`。这不是启动弹窗，也不在任务期间出现。

## 更新信任模型

默认更新发现使用 GitHub Releases API 的 `repos/BennyThink/NFCX/releases/latest`。客户端只接受非 draft、非 prerelease 的版本，按精确平台文件名选择 asset，并要求 API 返回 SHA-256 `digest`；下载完成后重新计算 digest。GitHub 的 HTTPS API 和仓库发布权限是第一阶段的信任边界。

实现必须：

- 正确比较 SemVer，不得以字符串相等或 tag 是否不同判断更新；默认忽略 prerelease。
- 确认当前平台和架构有匹配 asset，且 URL 使用 HTTPS、位于 GitHub 发布允许列表域名中。
- 将下载写入任务专用 staging 文件，流式计算 SHA-256，匹配后才改名为 prepared artifact。
- 对解压后的包再次验证文件清单、平台代码签名和版本，防止发布资产错误或解压替换攻击。
- 所有失败文件留在受限临时目录，可从 UI 删除；不得执行、装载或启动未验证文件。

## 本地状态与隐私

在平台配置目录新增独立的 `updates.json`，权限至少与现有遥测设置相同。它只保存检查时间、退避、用户抑制的版本、下载进度/预备 artifact 标识、自动下载偏好和待确认的更新事务；不得保存 URL query token、HTTP headers 或 NFC 数据。

退出或启动时需恢复“已下载、未应用”的事务，并再次校验 artifact，不信任上次进程留下的内存状态。缓存应有大小上限，并只清理 NFCX 自己的更新 staging 目录。

## 平台应用策略

更新由随应用签名分发的最小化 `NFCX Updater` 辅助程序执行。主程序只负责下载、验证、协调退出；辅助程序等待主进程退出、原子替换、保留一份短期回滚副本并重新启动 NFCX。辅助程序只接受经过认证的本地事务文件，不接受 GUI 传入的任意命令或路径。

| 平台与分发形式 | 自动应用条件 | 应用方式 | 不满足条件时 |
| --- | --- | --- | --- |
| macOS `.app` | app 位于可写位置，旧版和新版均通过 Apple 签名验证 | 将经过验证的 `.app` archive 解压到同一卷，辅助程序替换 bundle 后重启 | 保留下载并显示文件；不尝试绕过权限、提权或修改 Gatekeeper 设置 |
| Windows 私有 ZIP 安装目录 | 当前目录可写，旧版和新版 Authenticode 验证成功 | 辅助程序在主程序退出后解压并原子替换应用目录，再重启 | 保留下载并显示文件；不请求 UAC 来覆盖未知安装器管理的目录 |
| Linux AppImage | 当前 AppImage 可写、同文件系统原子替换可用、签名/哈希均有效 | 替换 AppImage，保留执行位，再重启 | 保留下载并显示文件 |
| Linux tar.gz、开发构建、未签名构建 | 不支持 | 不尝试自动替换 | 只提供手动下载文件 |

为支持该流程，发布管线除现有 DMG/ZIP/AppImage/tar.gz 外，必须生成仅供 updater 使用、内容完全等价的 macOS `.app` archive，并在 GitHub Release 的 asset digest 和签名证据中记录它。DMG 继续作为人工安装体验，不作为自动更新输入。

替换后，新版启动必须在 UI 初始化完成后写入“启动确认”。若在限定时间内未确认，辅助程序恢复备份并重启旧版。回滚只处理启动/替换失败，不能替代完整功能兼容性测试。

## 架构边界

- `internal/update`：GitHub Release DTO、SemVer、digest 校验、下载、状态机、staging 和平台 updater 协议；不得依赖 Wails 或 NFC reader。
- `internal/update/platform`：受限的 OS 文件替换和重启策略；不得直接暴露给 GUI。
- `app`：把可序列化的更新状态 DTO 和用户意图绑定到 Wails；负责根据工作台/任务状态决定是否允许重启。
- `frontend`：仅渲染状态和发起用户动作；不得自行 fetch feed、验证 hash、操作文件或调用外部 URL。
- 发布脚本：产出 asset、GitHub digest 与辅助程序签名证据。

更新操作应有可判定错误码，例如 `network_unavailable`、`release_untrusted`、`asset_not_supported`、`verification_failed`、`apply_not_permitted` 和 `apply_failed`；GUI 不得以错误字符串决定状态。

## 测试

- SemVer：稳定版、前置版本、build metadata、降级和相等版本。
- GitHub Release：结构上限、draft/prerelease 拒绝、缺失 digest、错误平台 asset 和错误 digest。
- 下载：取消、超时、重定向域名拒绝、大小上限、hash 不匹配、磁盘错误和恢复下载事务。
- 状态机：24 小时节流、退避、用户隐藏版本、手动检查、自动下载偏好及重启限制。
- 应用协议：攻击者可控路径、替换中断、旧程序未退出、新版未确认和回滚；所有测试使用临时目录与假辅助程序。
- app DTO 与前端：中英文状态、顶栏胶囊、About 状态、无活动任务/活动任务/脏工作副本的按钮状态。
- 每个平台的原生 CI：验证辅助程序签名、发行 asset hash 及 staged apply 的 smoke test；真实 NFC 硬件不参与。

## 手工验收

1. GitHub Releases API 不可达时正常进入主界面，没有更新弹窗。
2. 有稳定更新时，主界面只出现顶部胶囊；About 显示下载动作和本地化说明。
3. 下载过程中仍可执行读卡工作流；运行 NFC 任务时不能重启安装。
4. 下载完成后选择“稍后”，关闭再打开应用，更新仍为已准备好。
5. 安全空闲时选择“重启并更新”，确认新版本启动且旧版不再运行。
6. 对 hash、签名、代码签名或 bundle manifest 任一篡改，更新均不会应用。
7. 无法写入应用位置时，UI 明确说明原因并提供已验证文件，不弹浏览器、不请求绕过权限。
8. 新版在确认窗口内无法启动时，旧版自动恢复且用户获得可理解的失败原因。

## 验收标准

- [ ] 更新通知不会在启动或发现版本时以模态方式打断用户。
- [ ] 只有用户选择或明确启用自动下载后才下载完整更新包。
- [ ] NFC 任务、危险写入确认和未保存工作副本绝不会被更新流程中断。
- [ ] 自动应用仅处理已验签、hash 校验、平台签名校验均通过的匹配平台 asset。
- [ ] 不受支持的安装形式优雅降级为本地文件交付。
- [ ] UI 不再依赖不可控的普通 HTML 外链完成更新。
- [ ] 三个平台的更新、失败和回滚路径均有自动测试与干净环境手工证据。
